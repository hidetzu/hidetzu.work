# コンテンツ基盤の再設計（設計書）

- 作成日: 2026-11-17
- 状態: 設計案（実装は次のフェーズで判断する）
- 関連 ADR: [0009](../adr/0009-separate-knowledge-and-learning-records.md)（Proposed）、[0010](../adr/0010-static-search-with-pagefind.md)（Proposed）
- 前提とした ADR: 0001〜0008

この設計書は、`/math`・`/ml` と、今後足す分野で共通に使える「知識ノート」の基盤を決めるためのもの。
目的は、数学ノート専用の高機能なシステムではない。個人が長期間、知識を蓄積・学習・公開するための、保守しやすい共通の仕組みにする。
既存の実装で足りる部分はそのまま使い、新しく足すものは最小限にする。

## 0. 調査の方法と限界

- リポジトリのソース（`astro.config.mjs`、`src/` 以下、`tests/`、`docs/`、CI、`wrangler.toml`、`public/`）を読み、`npm run build` の出力（`dist/`）を調べた。
- 本番（https://hidetzu.work ）に curl でアクセスし、`.html` 付きの URL とサイトマップの有無を確かめた。
- Pagefind は公式ドキュメント（pagefind.app/docs、GitHub Releases。2026-11-17 に参照）で仕様を確認した。
  **このサイトの HTML で Pagefind を実際に動かす試験はしていない**（作業環境でパッケージの取得が許可されなかったため）。
  検索について書いたことのうち、ドキュメントで確かめたことと、試作で確かめる必要があることは分けて書く（§6.6）。

### 1.3 Markdown と Content Collections

- Content Collections（`src/content.config.ts`）に `math` と `ml` の 2 つ。どちらも `glob` ローダーで `src/content/<分野>/**/*.md` を読む。MDX は使っていない。
- Markdown の処理系は Sätteri（Astro 7 の既定）。remark / rehype は使わない（ADR 0002）。独自の mdast プラグインが 3 つある（`src/lib/math-markdown.mjs`）。
  - `katexMath` — `$…$` / `$$…$$` をビルド時に KaTeX の HTML にする（`output: 'htmlAndMathml'`）
  - `cjkLineBreaks` — 日本語の改行で余計な空白が入らないようにする
  - `mathBlocks` — `:::theorem[名前]{#id}` などのコンテナディレクティブを `div.math-block` にする。証明の `origin` / `text` / `note`、主張の `source` の表示もここ
- ML のノートも同じ処理系とブロックを使う（`ml/[slug].astro` が `math.css` を読み込む）。

### 1.5 証明の出どころと依存関係

- 証明ごとの出どころは、ブロックの属性で本文の中に書く（`:::proof{origin=self text=ai note="…"}`）。`origin` は `self` / `self-reviewed` / `textbook` / `ai`（ADR 0005）。
- 主張の参考文献での番号は `source` 属性（ADR 0008）。
- `src/lib/math-graph.mjs` が全ノートの Markdown を読み、証明の中のリンクから「証明で使う定義・定理」を集める。ノートページの「証明の依存関係」と、`/math` の「Dependencies」と出どころ別の証明数に使う。参照は一方向（ADR 0006）。
- 未解決の問いは `:::question`、途中の証明は `:::attempt`。

### 1.6 学習記録の現状

- ページ全体の状態: frontmatter の `status`（ノートの冒頭の Status 欄に出る）。
- 参考文献のどこを学んだか: `textbook` と `sources`（Study log 欄・Sources 欄、`/math#references`）。
- 学習の経過・証明の経緯・未着手の演習: 全 13 ノートとも本文末尾の `## 学習記録`（2026-11-17 の PR #32 で移した）。
- `/math` の「Now」に学習中のノートと出どころ別の証明数、「Roadmap」に今後の予定。
- ML のノートは、本文の冒頭に「このノートの書き分け」「学習の記録」「理解の状況」の表がある（数学とは書き方が違う）。

### 1.7 SEO・OGP・検索

- `Base.astro` が title、description、canonical、OGP（`og:image` は全ページ共通の `ogp.png`）、`twitter:card` を出す。ノートのページは `og:type=article`。
- サイトマップはない（`/sitemap.xml` は 404）。`robots.txt` は全許可で、サイトマップの記載なし。
- 構造化データ（JSON-LD）はない。
- サイト内検索はない。検索に使える依存ライブラリも入っていない。

### 1.8 デザイン

- 中央 56rem の 1 カラム。色は CSS 変数（`--fg` / `--body` / `--muted` / `--faint` / `--accent`）で、ダークモードは `prefers-color-scheme`。Web フォントは KaTeX だけ。
- スマートフォン幅の切り替えは `max-width: 40rem`。
- ノートの目次は本文の前に置いた入れ子のリスト（`nav.math-toc`）。サイドバーはない。

## 2. 現在の課題

1. **ノートの冒頭が重い。** タイトルと説明の直後に Status / Study log / Created / Updated / Sources / Tags の表があり、その下に目次がある。本文に入るまでに 1 画面以上かかるノートがある。
2. **知識と学習記録が同じページに混ざっている。** `## 学習記録` は末尾にまとめたが、ノートを開いた人が読む本文と、本人の振り返り用の記録が同じ流れにある。学習記録を分野全体で見渡す場所もない（`/math#references` は章立てとの対応だけ）。
3. **探せない。** 分野と章立ての一覧はあるが、言葉で探す方法がない。ノートが増えるほど、「写像」「逆像」のようにいくつものノートに出てくる概念を探しにくくなる。
4. **math と ml で共通部分が重複している。** 2 つの `[slug].astro` はヘッダー・メタ情報・目次の作りがほぼ同じだが、別々に書いている。frontmatter の共通部分（title、description、日付、tags）も別々に定義している。参考文献の属性名と形が違う（`sources` と `references`）。
5. **別名がない。** 「排他的論理和」と「XOR」、「写像」と「関数」のように、同じものを別の言葉で探す手段がない。
6. **分野を足す手順が決まっていない。** 新しい分野を足すと、コレクション、`[slug].astro`、一覧ページ、CSS をまた一から書くことになる。
7. **予約したい URL とノートの slug がぶつかりうる。** `/math/search`、`/math/learning` を足すと、同名のノートを作ったときに衝突する（`notation` も同じ）。今は検出していない。

## 3. 情報アーキテクチャ

### 3.1 3 種類のページ

| 種類 | 例 | 役割 | 置かないもの |
| --- | --- | --- | --- |
| 分野トップ | `/math`、`/ml` | 分野の説明、分野ごとの一覧、検索の入口、最近更新したノート、（必要なら）学習マップ | 個々の証明の経緯、章ごとの詳しい学習状況 |
| 知識ノート | `/math/propositional-logic` | 定義・例・定理・証明・考察。目次、関連ノート、参考文献 | 学習の経過、未着手の演習、状態の推移 |
| 学習記録 | `/math/learning` | 読んだ参考文献と範囲、ノートの状態、証明の出どころの集計、未解決の問い、学習の経過 | 定義や証明の本文 |

これに分野ごとの検索（`/math/search`、`/ml/search`）と、将来のサイト全体検索（`/search`）が加わる。

### 3.2 何をどこに置くか

| 情報 | 知識ノート | 学習記録 | 理由 |
| --- | --- | --- | --- |
| 定義・定理・証明・例 | 本文 | — | 記事の主役 |
| 証明ごとの出どころ（`origin` / `text` / `note`） | 証明の見出しの行（今のまま） | 出どころ別の集計 | 証明と切り離すと何の出どころか分からなくなる。本文には小さく出すだけにする |
| 主張の参考文献での番号（`source`） | 主張の見出しの行（今のまま） | — | 主張と一緒に見るもの |
| 参考文献（`sources`） | 本文の後の「参考文献」欄 | 参考文献ごとの章・節の一覧 | 読者が出典を確かめられるように両方に出す |
| ページの状態（`status`） | タイトルの下に 1 行（ラベルだけ） | 一覧 | 読む前に「どれくらい確かなノートか」は分かるようにする。説明は学習記録に |
| 学習の経過（今の `## 学習記録`） | 「学習記録を見る」へのリンクだけ | 本文 | 知識と学習記録の分離 |
| 未解決の問い（`:::question`） | 本文（今のまま） | 一覧（ノートへのリンク） | 問いは内容の一部。一覧で見渡せるようにする |
| 作成日・更新日 | タイトルの下に小さく | 一覧 | |

### 3.3 URL

- 既存の URL（`/`、`/math`、`/math/<slug>`、`/math/notation`、`/ml`、`/ml/<slug>`）、アンカー、`_redirects` はすべて変えない。
- 足す URL: `/math/learning`、`/math/search`、`/ml/search`、（将来）`/search`。ML の学習記録は、今のところ `/ml` の学習マップがその役割を担っているので、新しい URL は作らない（§3.5）。
- `/math#references`（旧 `#textbook`）は、学習記録のページへ移したあとも、`/math` に短い節とリンクを残して切らない。
- ノートの slug に `search`、`learning`、`notation` を使えないようにし、使ったらビルドで落とす（課題 7）。

### 3.4 分野トップ（/math）の構成

上から順に:

1. 見出しと 1〜2 段落の説明（今の lead を短くする。長い説明は学習記録へ）
2. 検索ボックス（`/math/search` へ。JS が動かなくても `/math/search?q=…` へのフォーム送信として成り立つようにする）
3. 分野ごとのノートの一覧（主な導線。今の Fields）
4. 最近更新したノート（3〜5 件）
5. 補助的な入口: 記号・文字リファレンス、学習記録（`/math/learning`）、ノート間の依存関係

今の Now（出どころ別の証明数）、References（章立て）、Legend（表示の意味）、Roadmap は学習記録のページへ移す。
Dependencies はノートを探す手がかりにもなるので、`/math` に残すか学習記録へ移すかは試作で決める。

### 3.5 数学と ML の違いを残す

- ML の `/ml` は学習マップ（領域・矢印・年表）が主役で、ノートは 1 つしかない。ノートの書き方も「ChatGPT との対話の記録」で、数学の「証明の出どころ」とは別の記録の仕方をしている。
- 共通にするのはノートのページの骨格（ヘッダー、目次、本文、参考文献、関連、学習記録へのリンク）と検索だけ。学習記録の形（数学: 証明の出どころと章立て、ML: 領域の状態とテーマごとの理解）は分野ごとに持つ。
- ML のノートの冒頭にある「学習の記録」「理解の状況」の表は、ML のノートが増えて困るまで動かさない。

- 「今読んでいる節」の強調は JS が要るので、今回は入れない。

## 5. コンテンツデータモデル

### 5.1 方針

- **Content Collections は維持し、分野ごとのコレクションのまま**にする。共通の属性だけを 1 つのスキーマ部品にまとめ、各コレクションがそれを広げて使う。
- 既存の属性名（`topic`、`createdAt`、`sources` など）は変えない。名前をそろえるための全ノートの書き換えはしない。
- 数学固有の属性（証明の出どころ、`textbook`、状態の値）は数学のコレクションにだけ置く。ML に強制しない。

### 5.2 共通の属性

| 属性 | 型 | 必須 | 意味 | 既存との関係 |
| --- | --- | --- | --- | --- |
| `title` | string | ○ | タイトル | 既存 |
| `description` | string | ○ | 概要（一覧・meta description・検索結果） | 既存 |
| 分類 | 分野ごとの enum | ○ | 分野の中の分類 | math は `topic`、ml は `area`。名前はそのまま |
| `order` | number | | 分類の中の並び順 | 既存 |
| `tags` | string[] | | タグ | 既存 |
| `aliases` | string[] | | 別名・英語名・略称（例: `XOR`、`exclusive or`） | **新規**。検索とノートの冒頭に使う |
| `related` | string[] | | 関連ノート | math は既存。ml にも足す（同じ分野の中だけ。分野をまたぐ関連は今は作らない） |
| `sources` | {title, location?, note?, year?, url?}[] | | 参考文献 | math の `sources` と ml の `references` の和。ml は当面 `references` のまま読み、移すかは後で決める |
| `createdAt` / `updatedAt` | date | ○ / | 作成日・更新日 | 既存 |
| `draft` | boolean | | 下書き | 既存 |

`subject` は、math の `topic`・ml の `area` と役割が重なるので足さない。分野（math / ml）はコレクションとディレクトリで決まるので、属性にはしない。

### 5.3 分野固有の属性

| 分野 | 属性 | 備考 |
| --- | --- | --- |
| math | `status`（5 段階）、`textbook` | そのまま。学習記録のページの材料 |
| math | 本文の `origin` / `text` / `note` / `source` / `ref` | ブロックの属性。変えない |
| ml | `status`（4 段階）、`progress` | そのまま |

### 5.4 本文・参考文献・学習記録の関係

```
知識ノート（src/content/math/<slug>.md）
  frontmatter: 共通属性 + status, textbook
  本文: 定義・定理・証明（origin / source 付き）・例・問い
        └ 証明の中のリンク ──→ math-graph が依存関係を集める
  （末尾の ## 学習記録 は、段階 3 で下の学習記録ファイルへ移す）

学習記録（src/content/math-log/<slug>.md）※段階 3 で導入
  frontmatter: note（知識ノートの slug。存在しなければビルドで落とす）
  本文: 学習の経過・証明の経緯・未着手の演習（今の ## 学習記録 の中身をそのまま移す）

/math/learning は、上の 2 つ + math.json（references, roadmap）+ math-graph（出どころの集計、:::question）から作る
```

学習記録を別のコレクションにする理由と代替案は ADR 0009 に書いた。

### 5.5 Content Collections の比較

| 案 | 内容 | 長所 | 短所 | 判断 |
| --- | --- | --- | --- | --- |
| A. 維持＋共通部品 | `math`・`ml` のコレクションのまま、共通属性を `baseNote` のような zod オブジェクトにまとめて `extend` する | 既存のノート・URL・型をそのまま使える。変更が小さい。分野ごとの違いを素直に書ける | 分野を足すたびにコレクションの定義が 1 つ増える | **採用** |
| B. 1 つの `notes` コレクションに統合 | `src/content/<分野>/<slug>.md` を 1 つのコレクションで読み、分野で判別するユニオン型にする | 横断の一覧・検索が書きやすい | 分野固有の属性で判別ユニオンが複雑になる。`id` が `math/xxx` になり、既存の `getCollection('math')`・グラフ・リンク検査を広く書き換える | 不採用 |
| C. Collections をやめて独自ローダー | `import.meta.glob` などで自前で読む | 自由度が高い | スキーマ検証・型・`render()` を作り直すことになる | 不採用 |
| D. MDX へ移行 | `.mdx` で Astro コンポーネントを本文に埋め込む | 本文に対話的な部品を置ける | 今のディレクティブで足りている。Sätteri の mdast プラグインとの組み合わせを検証し直す必要がある。依存が増える | 今回は不要。必要になった時点で別に検討 |

## 6. 検索アーキテクチャ

### 6.1 方式

**Pagefind を、ビルドの後に静的な索引を作る方式で使う**（ADR 0010）。サーバーや外部の検索サービスは使わない。

```
astro build ──→ dist/*.html
                  │
pagefind --site dist ──→ dist/pagefind/        （索引と UI。Math・ML の両方を 1 つの索引に）
                  │
/math/search  ──→ ブラウザで pagefind.js を読み、filters: { area: "math" } を付けて検索
/ml/search    ──→ 同じ索引を filters: { area: "ml" } で検索
/search（将来）──→ 同じ索引をフィルタなしで検索
```

`package.json` の `build` を `astro build && pagefind --site dist` にすれば、CI と Cloudflare Workers Builds（ビルドコマンドは `npm run build`）の両方で索引が作られる。

### 6.2 何を索引に入れるか

| 対象 | 方法 |
| --- | --- |
| ノートの本文 | `<article>` などノート本体の要素に `data-pagefind-body` を付ける。付けたページだけが索引に入る（Pagefind の仕様で、どこかに `data-pagefind-body` があると、付いていないページは索引に入らない） |
| タイトル | `h1` は自動で `title` のメタデータになる。メタデータは検索対象で、既定でタイトルの一致は重みが高い |
| 別名（`aliases`） | ノートの冒頭に「別名: XOR, exclusive or」と**見える形で**出し、その要素を `data-pagefind-body` の中に入れる。隠しテキストは使わない（§6.4） |
| 分野のフィルタ | `data-pagefind-filter="area:math"` をノートのページに付ける |
| 入れないもの | ヘッダー・フッター・パンくず（`data-pagefind-body` の外）、目次（`data-pagefind-ignore`）、証明の依存関係の一覧（ほかのノートのタイトルが並ぶため。`data-pagefind-ignore`） |
| 数式 | KaTeX の出力は `exclude_selectors` で除く（§6.3） |
| 一覧ページ | `/math`、`/ml`、`/math/notation` は当面入れない。`/math/notation`（記号の読み方）を入れるかは試作で決める |

### 6.3 数式の扱い

KaTeX は `output: 'htmlAndMathml'` で、見た目用の HTML と、読み上げ用の MathML（TeX のソースを `<annotation>` に持つ）の両方を出している。論理の基礎だけで `<annotation>` が 397 個ある。
そのまま索引に入れると、`\Rightarrow` のような TeX のソースや、記号が 2 重に入った文字列が検索結果の抜粋に出る。

- 第一案: `exclude_selectors` に `.katex` を指定し、数式を索引から外す。数式の中の文字（$P \oplus Q$ など）では探せなくなるが、本文の言葉で探せれば足りる。
- 代替案: `.katex-html` と `annotation` だけを外し、MathML の文字を残す。抜粋がどう見えるかを試作で比べる。
- KaTeX の出力を `html` だけにする案は、スクリーンリーダーで数式が読めなくなるので採らない。

### 6.4 別名

Pagefind のドキュメントには、見えないが検索できる文字列（同義語）を足す方法は書かれていない。
`data-pagefind-meta` は検索対象になるが、隠した要素で使う方法はドキュメントで保証されていない。

そのため、`aliases` は**ノートの冒頭に見える形で出す**。読者にも「XOR とも呼ぶ」ことが分かり、検索と表示が食い違わない。
`aliases` を使うのは、本文に出てこない言い方（英語名・略称）だけにする。本文にすでにある語は書かない。

### 6.5 分野の限定

| 案 | 内容 | 判断 |
| --- | --- | --- |
| A. 1 つの索引＋フィルタ | 全ノートを 1 つの索引に入れ、`area` のフィルタで絞る | **採用**。`/search` にそのまま広げられる。索引の作成は 1 回 |
| B. 分野ごとに別の索引 | `pagefind --glob "math/**/*.html" --output-subdir pagefind-math` を分野ごとに実行 | 混入が構造的に起きない利点はあるが、`/search` のためにもう 1 つ索引が要り、ビルドの手順が分野の数だけ増える。A で混入しないことを受け入れ基準で確かめられれば不要 |
| C. 外部の検索サービス（Algolia など） | | 不採用（バックエンド・外部サービスを足さない原則 9） |

Pagefind の UI 部品には、フィルタを最初からかけておく設定がドキュメントで見つからなかった。
そのため、`/math/search` は Pagefind の JS API（`pagefind.search(q, { filters: { area: 'math' } })`）を直接呼ぶ小さなスクリプトで作る。
UI 部品（Component UI）を使うのは、フィルタを既定で固定できることを確かめられた場合だけにする。

ML のノートは 1 つしかないので、`/ml/search` は ML のノートが増えたときに作ればよい。索引には最初から ML のノートも入れる（`/math/search` に混ざらないことの試験に使える）。

### 6.6 確かめたことと、試作で確かめること

ドキュメント（pagefind.app/docs、2026-11-17 参照）で確かめたこと:

- 最新は v1.6.0（2026-11-01）。日本語は、npm の `pagefind`（extended 版）で単語に分割して索引を作る。検索語は 1.5.0 以降、ブラウザの `Intl.Segmenter` で分割する。日本語の語幹処理（stemming）はない。
- 言語は `<html lang>` で判定する。このサイトは全ページ `lang="ja"`。
- `data-pagefind-body`、`data-pagefind-ignore`、`exclude_selectors`、`data-pagefind-filter`、`data-pagefind-weight` がある。nav・footer は既定で除かれる。
- 索引は分割され、検索時に必要な部分だけを読み込む。UI の JS・CSS は `dist/pagefind/` に出力され、CDN は要らない。
- Component UI は WAI-ARIA の慣習に従い、キーボード操作と IME の入力に対応している（1.5.0 以降）。

試作で確かめること（確かめるまでは前提にしない）:

- v1.6.0 のリリースノートに「日本語の分割はまだ完全ではない。カタカナの扱いは改善中」とある。§9.2 の検索ケースで、とくに「稠密性」（本文では「稠密性」と「稠密」の両方が出る）と「写像」「逆像」の結果を確かめる。
- `build.format: 'file'` のため、結果の URL は `/math/sets.html` になるはず。本番では `/math/sets.html` は 307 で `/math/sets` に転送されるので壊れはしないが、転送を 1 回挟む。表示の前に `.html` を取り除く（自前のスクリプトなら 1 行で済む）。
- 抜粋に数式の残骸や、目次・依存関係の文字が出ないこと。
- 索引のサイズと、1 回の検索で読み込む量。
- 版の固定: 導入時点で 2 週間以上前の版を `package.json` に固定する（1.6.0 は 2026-11-01 公開なので、すでに条件を満たす）。

### 段階 3: 学習記録の分離

## 9. テスト・受け入れ基準

### 9.1 レイアウトの変更（段階 1・4）

- `npm run check`、`npm test`、`npm run build` が通る。
- **本文が変わっていない**: 変更前後の `dist/math/<slug>.html` から `<article class="prose">` の中身を取り出して比べ、差分がない（数式・アンカー・ブロック・出どころの表示を含む）。比較するスクリプトを `tests/` に足すか、PR の確認手順に書く。
- `dist` の全ページで、内部リンクとアンカーが切れていない（既存のリンク検査。既知の例外は `404.html` の `#main` だけ）。
- 既存の URL（`/math/*`、`/ml/*`、`_redirects` の 3 件）が今までどおり 200 か 301 を返す。
- スマートフォン幅（390px）・PC 幅（1280px）・ダークモードで、横にはみ出さない。目次のサイドバーが本文と重ならない。ページ内リンクで飛んだ先が見出しの陰に隠れない。
- キーボードだけで目次の開閉・移動ができる。

### 9.2 検索（段階 2）

次の検索ケースで、期待するページが結果に出て、`/math/search` に ML のページが出ないこと。
期待するページは、2026-11-17 時点の `dist` で、数式と HTML タグを除いた本文に語が含まれるもの（`/math` などの一覧ページを除く）。

| 検索語 | `/math/search` で出るべきノート | 出てはいけないもの | 確かめること |
| --- | --- | --- | --- |
| 有理数 | 有理数の稠密性、位相の基底と生成される位相、整数と実数、位相空間の定義と位相の強弱 | ML | 有理数の稠密性が上位に来る |
| 稠密性 | 有理数の稠密性、位相の基底と生成される位相、整数と実数 | | 「稠密性」と「稠密」の両方で探せる |
| 排他的論理和 | 論理の基礎、集合の基本と演算 | | |
| XOR | 論理の基礎 | **`/ml`（年表に XOR がある）** | 英字の語。分野の限定の試験 |
| 写像 | 写像、直積、集合族、有限集合、整数と実数、関係、集合の基本と演算の 7 ノート | | 写像のノートが上位に来る |
| 逆像 | 「写像」と同じ 7 ノート | | |
| Transformer | （なし） | **`/ml`** | `/math/search` では 0 件。`/ml/search` を作ったら ML 側で出る |

そのほか:

- 抜粋に TeX のソース（`\mathbb` など）、目次・パンくず・フッターの文字が出ない。
- 結果のリンクが `.html` なしの URL を指し、アンカー付きの結果は正しい位置に飛ぶ。
- JS を切ると、検索ページに案内と `/math` へのリンクが出る。
- キーボードだけで、入力 → 結果 → ページを開く ができる。件数の変化が読み上げられる。IME で変換中に検索が走って入力を壊さない。
- 検索ページ以外の HTML に `<script>` が増えていない。

### 9.3 学習記録の分離（段階 3）

- 移す前後で、各ノートの `## 学習記録` の文章が、学習記録のページに一字一句同じに出る。
- `/math#references`、`/math#textbook` へのリンクが切れない。
- 出どころ別の証明数の合計が、移す前の `/math` の Now と同じ。

## 10. 想定されるリスク

| リスク | 影響 | 対策 |
| --- | --- | --- |
| Pagefind の日本語の分割が不十分（とくに複合語・カタカナ） | 「稠密性」などで期待するノートが出ない | 段階 2 の前に §9.2 で確かめる。足りなければ `aliases` を見える形で補う。それでも足りなければ導入を見送る |
| クライアント JS 0 の方針を崩す | 以後「少しなら JS を足してよい」と広がる | ADR 0010 で範囲を検索ページだけに限り、README に明記する |
| Pagefind のバイナリを npm から取る | Cloudflare のビルド環境で取得に失敗するとデプロイが止まる | 版を固定する。最初のデプロイで Workers Builds のログを確認する。失敗したら索引の作成を外しても他のページは出る構成にしておく |
| 新しいレイアウトで本文が変わる | 数式・アンカー・出どころの表示が壊れる | 本文の HTML の差分を受け入れ基準にする（§9.1） |
| 試作の見た目と既存の見た目が並存する期間が長引く | 2 種類のレイアウトの保守 | 段階 4 で広げる時期を決めておく。並存はノート単位の切り替えだけにする |
| 学習記録を移すときに文章が変わる | 記録が失われる・意味が変わる | 移すだけの PR にし、文字列の一致で確かめる（§9.3） |
| `/math/search` などがノートの slug と衝突 | ビルドで片方が上書きされる | 予約語の検査（段階 1） |
| 索引の肥大 | 検索が遅くなる | 数式を除く。ノートが 100 を超えたら索引のサイズを測る |
| 本の内容に近い表現を検索で見つけやすくなる | 著作権上の確認が済んでいない箇所が目立つ | 検索とは別の課題として、ADR 0008 の「残る課題」の照合を進める |
