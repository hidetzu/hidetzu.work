# ADR 0010: サイト内検索を Pagefind で作り、検索ページだけでクライアント JS を使う

- Status: Accepted（2026-11-17。JS の例外と Pagefind の導入を本人が承認）
- Date: 2026-11-17
- 関連: [ADR 0002](0002-add-math-notes.md)、[設計書](../design/content-platform.md) §6

## 背景

数学ノートが 13 になり、「写像」「逆像」のように複数のノートに出てくる概念を探しにくくなった。
分野ごとの検索（`/math/search`、`/ml/search`）と、将来のサイト全体検索（`/search`）がほしい。

このサイトは静的サイトで、README の「実装の方針」でクライアント JS を 0 にすると決めている。
静的サイトで全文検索をするには、ブラウザで動く JS が要る。

## 決定

1. Pagefind を使う。`astro build` のあとに `pagefind --site dist` で索引を作り、`dist/pagefind/` に出力する。`build` スクリプトに含め、CI と Cloudflare Workers Builds の両方で作る。
2. 索引はサイト全体で 1 つにし、ノートのページに `data-pagefind-filter="area:<分野>"` を付ける。分野の検索ページは、そのフィルタを付けて検索する。
3. 索引に入れるのはノート本体（`data-pagefind-body`）だけ。目次・証明の依存関係の一覧は `data-pagefind-ignore`、KaTeX の出力は `exclude_selectors` で外す。
4. 別名（frontmatter の `aliases`）は、ノートの冒頭に見える形で出して索引に入れる。見えない文字列は使わない。
5. **クライアント JS は検索ページ（`/math/search` など）でだけ読み込む。** 分野トップの検索ボックスは、JS なしで検索ページへ送るフォームにする。検索ページは、JS が動かないときに案内と一覧ページへのリンクを出す。README の「クライアント JS は 0」を、この例外を含む書き方に直す。
6. 検索ページの UI は、Pagefind の JS API を呼ぶ小さなスクリプトで作る。Pagefind の UI 部品は、分野のフィルタを既定で固定できると確かめられたら置き換えを検討する。
7. Pagefind の版は `package.json` で固定する。

導入は、設計書 §9.2 の検索ケース（有理数、稠密性、排他的論理和、XOR、写像、逆像、Transformer）を試作で確かめてから決める。
とくに日本語の分割（Pagefind 1.6.0 のリリースノートに「まだ完全ではない」とある）で期待する結果が出なければ、導入を見送る。

### 試作で確かめたこと（2026-11-17、Pagefind 1.6.0、ローカルのヘッドレス Chrome）

Pagefind の通常の検索は、次のように関係のないノートを返した。

- 「Transformer」→ 論理の基礎（真理値表の「T」に一致）
- 「逆像」→ 直積・関係（「逆」「像」に分けて、「逆向き」「写像」に一致）

引用符で囲んだ完全一致（`"逆像"`）では、本文にその語を含むノートだけが出た。そのため、検索ページは次のようにした。

- まず語ごとの完全一致で探し、0 件のときだけ通常の検索を「近い語」として出す。そのことを件数の文で明示する
- 近い語の結果のうち、1 文字だけの一致しかないものは出さない
- タイトルに検索語を含むノートを先に出す

結果（`/math/search`）は次のとおり。

| 検索語 | 結果 |
| --- | --- |
| 有理数 | 有理数の稠密性、位相の基底と生成される位相、整数と実数 |
| 稠密性 | 同じ 3 ノート |
| 排他的論理和 | 論理の基礎 |
| XOR | 論理の基礎（`/ml` の年表には出てくるが、索引に入れていない。ML のノートは `area` のフィルタで除かれる） |
| 写像 | 写像（先頭）、関係、有限集合、直積、整数と実数 |
| 逆像 | 有限集合、写像 |
| Transformer | 0 件 |

本文に語を含むノートはすべて出た。設計書 §9.2 の表は関連ノートの欄まで数えていたので、それより少ない。

## 採用しなかった案

- **Fuse.js / MiniSearch などで、全ノートの本文を JSON にして読み込む** — ページが増えると最初に読み込む量が増える。日本語の分割を自前で作る必要がある。
- **Algolia などの外部の検索サービス** — 外部サービスと API キーの管理が増える。静的サイトの利点を損なう。
- **サーバーでの全文検索（Workers + D1 など）** — バックエンドを足さない方針に反する。
- **分野ごとに別の索引を作る** — 分野の混入は構造的に起きないが、`/search` のための索引が別に要り、ビルドの手順が分野の数だけ増える。フィルタで混入しないことを受け入れ基準で確かめる。
- **全ページのヘッダーに検索ボックスの JS を置く** — JS を読み込むページが全ページに広がる。

## 結果

- 検索ページだけ、Pagefind の JS と WebAssembly、索引の一部を読み込む。ほかのページは今までどおり JS 0 のまま。
- ビルドに Pagefind のバイナリ（npm から取得）が加わる。取得に失敗するとビルドが止まるので、最初のデプロイで Workers Builds のログを確かめる。
- 数式の中の文字では検索できない。

## 追記（2026-11-21）：ノートの目次の現在位置の強調

ノートのサイドバーの目次では、いま読んでいる節を CSS の `scroll-target-group` / `:target-current` で強調している。
これは Chrome / Edge でしか動かず、Firefox・Safari では強調されなかった。

決定 5 の例外として、ノートのページ（`NoteLayout`）にも小さなインラインスクリプトを置く（本人が承認）。

- `CSS.supports('selector(:target-current)')` が真のブラウザでは何もしない（CSS に任せる）
- 偽のブラウザでだけ、スクロール位置から節を求めて目次のリンクに `aria-current="location"` を付ける
- 外部ファイルやライブラリは読み込まない。JS が動かなくても、目次のリンクはそのまま使える

## 追記（2026-11-21）：ブロック単位の検索と、種類・分野の絞り込み

ノート単位の結果では、「有理数の稠密性」の証明を探してもノートの冒頭に着き、証明はページの中で探す必要があった。

- 索引は CLI（`pagefind --site dist`）ではなく、Node API で作る（`scripts/build-search-index.mjs`）。`pagefind.yml` の設定（`.katex` を除く）はスクリプトに移した
- ページ単位の結果（ノートと `/math/notation`）に加えて、ノートの定義・定理・証明・反例・例などのブロックを、ビルド後の HTML から 1 件ずつ取り出して `addHTMLFile` で入れる。URL はノートの中のブロックのアンカー
- アンカーのないブロックには、`src/lib/math-markdown.mjs` が本文の順と主張の id から決まる id を付ける（証明は `<主張の id>-proof`）。既存のアンカーは変えない
- フィルタに `kind`（定義・定理・証明・反例・例・節）と `field`（分野）を足し、検索ページで絞り込めるようにした。条件は URL に持つ
- 検索ページだけが JS を読み込むことは変わらない。結果の項目名の数式のために、検索ページで KaTeX の CSS を読む
